# PoliceLink 설계서 검토 (2026-11-15)

받은 설계서(「경찰 통합 긴급지원 플랫폼 개발 설계서」)를 **실제로 운영해 본 `emergency-ntfy`(환자 수용 요청)** 경험에 비추어 검토했습니다.
결론: **전체 방향(4가지 요청을 하나의 알림·응답 엔진으로 통합, 2단계 도입 전략, 최종 배정은 사람이 승인)은 타당합니다.**
다만 아래 항목은 그대로 만들면 동작하지 않거나 보안상 문제가 생기므로 고쳐서 1차 시험판에 반영했습니다.

## 1. 그대로 두면 안 되는 부분 (반영함)

| # | 설계서 내용 | 문제 | 1차 시험판에서 바꾼 것 |
|---|---|---|---|
| 1 | 2차에 "ntfy 알림, 미응답 재알림" 을 Apps Script 로 | **Apps Script 서버(UrlFetchApp)는 ntfy.sh 에 접속할 수 없음** (Google 차단, emergency-ntfy 에서 확인). 시간 트리거로 재알림을 보내는 방식은 불가 | 서버는 알림 **내용만 만들고**, 요청을 보낸 직원의 **브라우저가 ntfy.sh 로 직접 POST** (emergency-ntfy 와 같은 방식). 재알림은 **상황판(관제 PC) 브라우저가 1분마다** 서버에 물어보고 발송 — 잠금으로 여러 PC 가 열려 있어도 한 번만 |
| 2 | 알림 채널 구분 없음 | ntfy.sh 는 공개 서버. **토픽 이름을 아는 사람은 누구나 알림을 읽고 보낼 수 있음** (토픽 = 비밀번호). 메시지는 ntfy.sh 에 약 12시간 보관됨 | 알림에는 **요청번호 · 유형 · 긴급도만** (위치 · 사건 내용 · 이름 없음). 토픽은 **수신자마다 따로** 무작위 20자로 만들어 비공개 시트에만 저장 |
| 3 | 수신 그룹(지역·기관별) 공용 토픽 | 공용 토픽이면 외부 기관이 **다른 기관에 간 요청까지** 보게 됨 → "외부 수신자는 자신의 협조 요청만" 원칙 위반 | **수신자별 토픽 + 수신자별 개인 링크**(`?r=<토큰>`). 서버도 그 수신자가 대상인 요청만 돌려줌 |
| 4 | 1차는 "관리자·수신자 권한이 분리되지 않음" , 역할별 로그인은 6차 | 웹앱을 여러 사람이 쓰려면 "모든 사용자" 로 배포해야 하는데, 권한 분리가 없으면 **주소를 아는 누구나 관리자 기능 사용** 가능. "본인만 접근" 으로 배포하면 다른 휴대폰에서 시험 자체가 안 됨 | **1차부터 권한 분리**: 직원은 아이디 + PIN(해시 저장, 5회 실패 시 10분 잠금, 6시간 세션), 역할 = 관리자 · 상황관리자 · 현장 경찰관. 외부 수신자는 개인 링크(재발급 시 이전 링크 즉시 무효) |
| 5 | 요청에 사건 내용 한 칸 | 외부 기관에 보낼 내용과 내부 내용이 섞임 | **요청 내용(외부 전달용)** 과 **내부 메모(경찰 내부만)** 를 나눔. 외부 기관 화면 · 서버 응답에는 내부 메모 · 요청자 ID 가 아예 안 실림 |
| 6 | 알림을 누르면 앱 열기 | ntfy 는 **알림에 click 주소가 있으면 눌러도 계속 울림이 안 멈춤** (2026-10-25 시험) | click 없음. 알림 본문 → ntfy 화면(알람 멈춤) → **PoliceLink 열기** 버튼. 웹앱의 빨간 배너 · 응답 버튼으로도 알람 끄기 (emergency-ntfy 그대로) |
| 7 | Google Sheets 에 기록 | 사용자가 입력한 `=` 로 시작하는 글이 **수식으로 실행**될 수 있음 (수식 주입) | 모든 칸을 텍스트 형식으로 저장 + `= + - @` 로 시작하면 앞에 `'` |

## 2. 데이터 구조 조정

| 설계서 | 시험판 | 이유 |
|---|---|---|
| `PATROL_UNITS` 별도 표 | `RECIPIENTS` 에 통합 (`type=patrol`, `status`=가용/출동중/휴식, `zone`=담당 구역) | 순찰차도 **알림을 받고 수락/거절하는 수신자**. 두 표로 나누면 토픽 · 링크 · 상태를 두 곳에서 관리해야 함 |
| `RESPONSES` 1행 = 최종 응답 | **추가만 하는 기록** (가장 최근 행이 현재 응답) | 수락 → 거절로 바꾼 이력까지 남음 (감사 목적) |
| `ASSIGNMENTS` | 유지 + 재배정 이력 | 누가 언제 누구로 배정을 바꿨는지 |
| `REQUESTS` | `summary`(외부용) / `detail`(내부용) 분리, `realertCount` · `lastAlertAt` 추가 | 위 1-5, 1-1 |
| `USERS` | `pinHash` + `salt` (PIN 원문 저장 안 함) | 시트가 유출돼도 PIN 은 바로 알 수 없게 |
| `AUDIT_LOG` | 로그인(성공/실패) · 요청 · 응답 · 배정 · 완료 · 취소 · 재알림 · 계정/수신자 변경 모두 | 설계서의 감사기록 요구 |

## 3. 업무 측면에서 확인할 점 (코드로 해결되지 않음)

1. **금융기관 협조** — 계좌 · 거래 정보 제공은 「금융실명법」 등 법적 절차(영장 · 공문 등)가 필요합니다.
   이 플랫폼은 **"협조 요청이 있었다는 연락과 접수 확인"** 채널로만 쓰고, 금융정보 자체는 주고받지 않도록 했습니다 (응답 버튼도 "접수 확인 / 처리 불가").
   기관별 **공식 협조 창구**는 금융기관과 사전 협의로 정해야 합니다.
2. **순찰차 배치** — 공식 지령은 기존 112 시스템이 우선입니다. 두 시스템이 따로 배정하면 **이중 배정** 위험이 있으므로,
   시험판은 "보조 연락 · 상황 공유" 용도로 두고 최종 배정은 상황관리자 버튼으로만 했습니다.
   1차 추천은 GPS 없이 **가용 여부(+100) · 담당 구역(+30) · 진행 중 임무(−40/건) · 휴식(−50)** 으로 점수를 매기고, 긴급이면 상위 2대 · 보통이면 1대를 미리 선택합니다 (`recommendPatrol_`).
3. **통역원** — 통역원 개인 연락처는 개인정보입니다. 시험판은 연락처를 관리자만 보게 했고, 실제 연락은 ntfy + 회신 번호(상황실 대표번호)로 합니다.
4. **실제 도입** — 개인 Google 계정 · 공용 ntfy.sh 는 경찰 업무 데이터에 쓸 수 없습니다 (공공기관 클라우드 보안인증, 기관 보안성 검토 대상).
   설계서의 2단계 전략대로, 시험판은 **가상 데이터로 기능 · 화면 · 흐름만 검증**하는 용도입니다.

## 4. ntfy 를 계속 쓰는 것에 대해

ntfy 로 가는 것이 좋습니다. emergency-ntfy 에서 이미 확인한 장점:

- 화면 꺼짐 · **무음 모드에서도** 1~2초 안에 **알람 음량**으로 울림, 우선순위 5 + "계속 울리기" 로 **누를 때까지** 울림
- 무료 · 회원가입 없음 · 안드로이드 앱 안정적, 사이렌 소리 · 복원 파일로 빠른 설정 가능 (emergency-ntfy `phone-setup/`)
- 같은 `sequence_id` 로 보내면 앞 알림을 **바꿔치기** → 재알림 · 배정 확정 · 취소가 알림 하나로 정리됨 (요청번호를 sequence_id 로 사용)

실제 운영으로 갈 때 바꿀 것:

| 지금 (시험) | 운영 단계 |
|---|---|
| 공용 ntfy.sh, 토픽 이름이 곧 비밀번호 | **기관 서버에 ntfy 직접 설치**(오픈소스, Docker 1개) + `auth-default-access: deny-all` + 수신자별 읽기 전용 토큰 |
| 직원 브라우저가 ntfy 로 직접 발송 | 인증 · 보안 중계 서버가 발송 (발송 토큰은 서버에만), 내부망 ↔ 외부 알림 분리 |
| 알림 미응답 재알림 = 상황판 브라우저 | 중계 서버 스케줄러 |
| iPhone 은 계속 울리기 불가 | 수신 단말은 안드로이드로 통일하거나, iOS 수신자는 전화 · 문자 보조 채널 |

## 5. 단계별 계획 (조정안)

| 단계 | 내용 | 상태 |
|---|---|---|
| 1차 | 4종 요청 · 수락/거절 · 배정 · 완료 · 시트 기록 · **ntfy 알림 · 재알림 · 수신자별 링크 · 역할별 로그인 · 감사기록** | ✅ 이 저장소 (설계서 1~2차 + 6차 일부를 앞당김) |
| 2차 | 휴대폰 빠른 설정(ntfy 복원 파일, emergency-ntfy `phone-setup` 재사용) · 통계 화면 · 요청 템플릿 | 예정 |
| 3차 | 순찰차 위치(지도 API) · 이동 예상시간을 추천 점수에 추가 | 예정 |

| 6차 | 승인된 서버 · DB 로 이전, 암호화 · 보존기간 · 자체 ntfy | 기관 승인 필요 |
